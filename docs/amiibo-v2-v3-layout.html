How a rider, its machines and a save fit together

The rider is the amiibo. A machine is what the figure carries in its SRAM. Tested on a registered Kirby (Warp Star is its own machine) loaded with a Tank Star SRAM, then a fashion change and a back-out to save.

0x000–0x247

Rider data

One copy per amiibo. Owner, nickname, flags, counters and the KAR payload at 0xDC–0x1B3 (decrypted image). The payload belongs to the rider and differs between figures.

Every save rewrites the settings and a few payload bytes. The fashion change in the test changed 5 payload bytes and the counters.

0x248–0x387 and 0x400–0x7E7

Machine records

Ten slots. A slot holds the rider's record for one machine (a 32-byte value plus a 100-byte record). The slot is chosen by the machine that is attached, not by the rider.

0x3C0–0x3FF

Machine attached now

The SRAM block says which machine the rider is on. It is the figure's own machine unless we replace it. The game reads it on every scan and picks the slot from it.

In the test: Tank Star's SRAM on Kirby. The screen showed Kirby on a Tank Star, proficiency 0.

What happened in the test

  1. Load. Registered Kirby (slot 0 in use) with the SRAM of the Tank Star. The game accepts it and shows Kirby on a Tank Star.
  2. Change the fashion and back out. The game writes the amiibo. The dump read back from the dongle decrypts with valid hashes.
  3. Result. 554 bytes changed: the settings and rider data (0x12–0x33, 0xC0–0x247) and slot 4 in both regions (0x2C8–0x2E7 and 0x590–0x5F3). Slot 0 was not touched. So the record follows the machine, and a rider can hold up to ten machine records.

Slot numbers by machine come from seven figures that each registered on their own machine: Warp Star 0, Wing Star 1, Hop Star 2, Shadow Star 3, Tank Star 4, Dragoon 5, Hydra 6. Slots 7 to 9 are not seen yet. What the 32-byte and 100-byte values contain is not decoded.

How much is decryptable

v2 540 B
v3 2048 B

Green is the range covered by the amiibo-layer crypto: v2 bytes 0x000–0x207, v3 bytes 0x000–0x247 (584 of 2048).

Amiibo layer, done

AES-128-CTR over 392 bytes (0x014–0x033 and the 360-byte app data), HMAC-SHA256 for the tag and data hashes. The same retail key file works for both formats. v3 only changes where the HMAC and app data sit.

Game layer, not done

The KAR payload inside the app data, the blocks after 0x248 and the SRAM authentication bytes are not covered by the amiibo key. We keep them byte for byte so a decrypt followed by an encrypt returns the original file.

Things the dumps showed

  • Format is detected by size, and for encrypted v3 by the ID format byte at 0x05B being 03.
  • A decrypted v3 binary is 2048 bytes: the 520-byte internal layout, the 64 reserved bytes, then everything from 0x248.
  • Saved records follow the machine: Kirby on a Tank Star wrote slot 4 and left slot 0 alone. The rider's own payload stays in the main data.
  • The machine in Kirby Air Riders follows the SRAM block, not the encrypted data. Changing the UID is risky: with the payload's own machine the game shows error 2115-0548, and a UID the console has never seen gets "can't participate in matches". UIDs it already knows work (see the UID notes).
