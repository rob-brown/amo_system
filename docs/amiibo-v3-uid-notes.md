# Amiibo v3 UID notes (running log)

Working notes on how the UID behaves on v3 amiibo (NTAG I²C Plus 2K, Kirby Air Riders). Update this file as new scans and tests come in. Facts come from dumps and console tests; inferences are marked.

## Dumps analysed

| Dump | UID (tag bytes 0-6) | Byte 7 | Byte 8 | SRAM code (tag 0x3D3, 6 chars) | Machine in KAR |
|---|---|---|---|---|---|
| kirby.bin (unregistered) | `04 68 99 5A AB 1F 90` | `00` | `44` | `PB4W17` | Warp Star |
| metaknight-registered.bin | `04 67 39 5A EF 1F 90` | `00` | `44` | `PB5T42` | Shadow Star |
| dedede-registered.bin | `04 54 37 62 7C 20 90` | `00` | `44` | `PC6U55` | Tank Star |

Observations:

- Fact: bytes 0-6 are the 7 UID bytes with no BCC bytes. Byte 3 is not BCC0 (for Kirby, `04 ^ 68 ^ 99 ^ 88` is `7D`, not `5A`).
- Fact: UID0 is `04` (NXP). All three UIDs end in `90`, and UID5 is `1F`, `1F` or `20`.
- Fact: byte 7 is `00` and byte 8 is `44` in all three dumps. Inference: fixed fields, not UID flags.
- Fact: in v2, the "UID is 7 bytes" signal is the cascade tag `0x88`. It is never stored; it is folded into BCC0 (`0x88 ^ UID0 ^ UID1 ^ UID2`), and UID3 must not be `0x88`. In v3 dumps no such flag is stored. Inference: the cascade tag is handled on the wire by the NFC firmware.
- Constraints we apply to any UID we write: UID0 = `04`, UID3 != `0x88`.

## What NXP documents (NT3H2111_2211 data sheet rev 3.6, NTAG213/215/216 data sheet, AN10927)

Quoted or paraphrased from the data sheets; inferences are marked.

- The NTAG I²C Plus stores the 7-byte UID in the first 7 bytes (pages 00h-01h). UID0 is fixed at `04`. There are no BCC bytes in its memory map. Page 01h byte 3 and page 02h bytes 0-1 are "Internal", page 02h bytes 2-3 are the static lock bytes, and page 03h is the capability container.
- NTAG215 (v2) differs: its first 9 bytes hold the UID and two check bytes (`BCC0 = 0x88 ^ UID0 ^ UID1 ^ UID2`, `BCC1 = UID3 ^ UID4 ^ UID5 ^ UID6`). This is why a v3 dump has no BCC bytes.
- The cascade tag `0x88` is not stored on either chip. It is the anticollision framing byte (AN10927): cascade level 1 sends `88 UID0 UID1 UID2 BCC`, level 2 sends `UID3..UID6 BCC`. Inference: on the I²C chip the BCCs seen on the air are generated by the chip's RF front end. This matches our dumps, which have no length flag to preserve.
- NXP only requires UID0 = `04`. It says nothing about UID1-UID6, so the `90` suffix and UID5 pattern in our dumps are not NXP rules.
- Every UID is signed by NXP (ECDSA, secp128r1). The 32-byte signature sits in hidden memory and is read with `READ_SIG` (`3C 00`). The data sheet does not state the exact message signed. Our firmware returns 32 zero bytes, and the console still accepts the unmodified amiibo, so the console does not appear to verify it.
- SRAM: 64 bytes, volatile. The NFC side only sees it in pass-through mode (pages F0h-FFh of sector 0) or mirrored into user memory. The chip has no CRC, MAC or authentication over SRAM content, only the 16-bit CRC on each RF frame. Inference: any authentication bytes in the SRAM block come from whatever sits on the I²C side (an MCU in the figure), not from the NXP chip.
- Config pages on the 2K chip: dynamic lock E2h, AUTH0 E3h, ACCESS E4h, PWD E5h, PACK E6h, PT_I2C E7h, registers E8h-E9h, session registers ECh-EDh. Sector 1 is plain user memory. These are chip-level facts, not amiibo-specific.
- Public non-NXP sources (allmiibo-sync PROTOCOL.md section 10.6, Flashiibo manual; second-hand and unverified): dumps of the same character differ only in the SRAM-mapped pages F0h-FFh by 21-22 bytes, the vehicle is identified by a code such as `PB4W17` (Warp Star), `PB5T42` (Shadow Star) and `PC6V28` (Tank Star), and bytes 975-978 of the dump vary per physical tag. Our Tank Star code is `PC6U55`, so codes vary per figure or batch.

## How the UID feeds into our crypto

- The amiibo key seed is tag bytes 0-7 raw (`UID0..UID6, 00`). With the BCC form instead of raw bytes both HMAC checks fail. Verified on all three dumps.
- When the UID changes, `encrypt_binary` rederives the keys and recomputes the data HMAC and the tag HMAC, so the amiibo-layer integrity data stays valid.
- Not updated by us: the SRAM block `0x3C0-0x3FF` and anything inside the game-encrypted payload. See the rule below for how the game ties them to the UID.

## Dump structure learned so far

- The dump is a straight page dump: sector 0 is `0x000-0x3FF` (pages 00h-FFh) and sector 1 is `0x400-0x7FF`.
- `0x388-0x3B7` is the NTAG I²C Plus register area, identical on all three figures (dynamic lock page E2h, AUTH0 E3h, ACCESS E4h, PT_I2C E7h, config registers E8h-E9h, session registers ECh-EDh with pass-through on). It is not game data. The `0x710` config pages named in the earlier spec are zero in every dump. (Found by the advisor session.)
- `0x3C0-0x3FF` is the SRAM (pages F0h-FFh). Layout: `[0-1]` = `02 00`, `[2-14]` 13 bytes that differ per figure and are verified by the game, `[15]` = `00`, `[16]` `82`/`81`/`4A`, `[17]` = `00`, `[18]` `03`/`0A`/`11`, `[19-24]` code (`PB4W17`, `PB5T42`, `PC6U55`), `[25]` = `20`, `[26-28]` `01 01 02`/`04`/`04`, rest zero, `[62-63]` CRC-16.
- The SRAM CRC is CRC-16/MCRF4XX (poly `0x1021`, init `0xFFFF`, reflected in and out, no final XOR) over SRAM bytes 0-61, stored big-endian. It matches all three dumps. Flipping one bit of SRAM byte 2 with a corrected CRC makes the game report error 2115-0176 "This is not an amiibo", so the game verifies those bytes beyond the CRC.
- There are two slotted regions, 10 slots each, and a figure uses the same slot index in both: 32-byte slots at `0x248 + 32n` and 100-byte slots at `0x400 + 100n` (each starting `A5 00 01 00`). Kirby uses slot 0, Meta Knight slot 3, Dedede slot 4, matching Warp Star, Shadow Star and Tank Star. Inference: one slot per machine, holding saved progress. Offline checks (HMAC-SHA256 of the 100-byte slot under the raw and derived keys, AES-CTR with the derived keys) found no relationship on any dump.
- In the decrypted 2048-byte image, offsets at or after `0x248` equal tag offsets.

Findings:

- The machine comes from the SRAM block. Swapping SRAM while keeping the figure's own UID changed the machine and was accepted for all three figures. Registered data (nickname, fashion, FP level) survives the swap.
- Provisional model that fits every run so far (payload P, UID u, SRAM s):
  - Hard failure, error 2115-0548 (payload-side or save-side, not yet separated; the save-side version is: the scanned rider and machine pair is already registered to a different UID in the console's save): the SRAM's machine is the payload's own machine and the UID is not the payload's. Runs: (Kirby,d,k) (Kirby,m,k) (Kirby,random,k) and the slot and reserved-block variants of (Kirby,d,k).
  - A UID the console has seen before scans normally otherwise: (Kirby,k,d) (Kirby,k,m) (Kirby,d,d) (Kirby,m,m) (Kirby,m,d) (MK,m,k) (Dedede,d,m). The (Kirby,m,d) pass matters: that UID matches neither the payload nor the SRAM.
  - A UID the console has never seen, with a registered payload and a different machine, is read but flagged: "This amiibo can't participate in matches." Runs: (Kirby,random,d) (Kirby,random,m).
  - So the SRAM block is not what binds the UID. Inference: the console's KAR save keeps per-UID figure data, and a new UID would need the game's own registration step.
  - Caveat: all three UIDs were scanned on this console before. A never-registered UID with an unregistered payload has not been tested (the advisor's scan 2), and scanning under real UIDs may have changed what the console holds for the real figures.
  - Scan 1 from the advisor's plan: (Kirby, UID Meta Knight, SRAM Dedede) scans normally (Skirby on a Tank Star, no dialog).
- Settings flags: decrypted offset `0x2C` (tag `0x14`) is `0x30` on all three dumps (bits 4 and 5 set), so all three count as initialised and this byte is not a registered flag. The four bytes before it differ: Kirby `A5 83 F3 00`, Meta Knight and Dedede `A5 00 02 00`. The flag meanings come from the advisor's memory of yuzu's `amiibo_types.h`; that file is not on this machine, so they are unverified.
- Test that would separate payload-side from save-side 0548 without touching the main save: a second console user with a fresh KAR save scans (Kirby, random UID, SRAM Kirby) and (Kirby, random UID, SRAM Dedede). It needs the user.
- Swapping slot blobs or the reserved block did not change any result, so the payload-side binding is not in those regions (probably in the game-layer encrypted payload).
- Offline search: the UID, its last four bytes, the code string and the 13 SRAM bytes do not occur anywhere in the decrypted payload of any dump. They appear only at their known places (tag offsets 0 and 0x3C2/0x3D3). Only one byte of the app area (decrypted offset `0x1B0`) is equal in Meta Knight and Dedede but different in Kirby, probably the registered flag.
- Consequence: a brand-new UID is read but flagged as unable to join matches when the payload is registered. Whether an unregistered payload with a new UID gets registered by the game is untested.
- The game remembers a rider and machine combination in its session, which may affect repeat scans.

## Open questions

- Where the payload-side UID binding lives (the game-layer bytes `0xDC-0x1B3` of the decrypted image, or the slot blobs together with something else).
- Whether the slot index is derived from the machine and what the slots hold. The write path (the game saving FP data back into a slot) has not been exercised on the picopad.
- Whether the SRAM check is a MAC with a Nintendo key or a signature. Offline probes found nothing.
- Whether more figures (other riders and machines) follow the same rule. More dumps are expected.

## Side effects of testing

- Scans started from the KAR amiibo menu showed the "GOT IT!" figure unlock screen, so these main menu figures are now unlocked in the console's KAR save: Shadow Star & Kirby, Warp Star & Meta Knight, Shadow Star & King Dedede. This is cosmetic. The game returns to the title screen when left idle, which interrupts a test run.
