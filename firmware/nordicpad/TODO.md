# nordicpad TODO

State on 2026-11-14: the nRF52840 dongle runs BTstack plus the open-source Zephyr controller (patched `CONN_INTERVAL_MIN`), pairs as a Pro Controller 2, keeps its pairing in flash, and takes host commands over a second USB serial port. Buttons, both sticks and v3 amiibo reads (Kirby verified on the dongle) work on the console.

## Amiibo

- [x] **Writes.** Done and verified on the console (2026-11-14): the system registration (Enter Owner and Nickname) showed "Data saved" and the game's own FP save showed "Writing complete" (watched on screen for Kirby+WarpStar, Dedede+TankStar and Kawasaki+HopStar); all seven fresh Flashiibo v3 figures were run through the same scripted flow, read back changed and pass `decrypt_binary`. The sequence was decoded from a sniffed real Joy-Con 2 R (capture and scripts in `~/Documents/nordicpad-captures/2026-11-14-real-write/`): after the scan and an 80-byte `01.14` handshake plus `01.21` (SRAM, static), the console pre-reads page 3 (`01.06`, range 3..3), then sends **write A** (slot data, timeout 5000 ms: `01.14` pieces, then `01.20`; poll status 0x16) and **write B** (app data, `01.14` pieces, then `01.08`; poll status 0x05, then `01.04`). A `01.14` payload is `[offset16][length16][up to 76 bytes]`. Write B header is 21 bytes (`timeout16 uid7 01 06 01 04 ff ff ff ff a5 counter16 00`, the last four bytes are page 4), then a chunk count and `[page][size][data]` chunks (pages 5-12, 48-107, 108-145 on v3). Write A header is 22 bytes (the last four bytes are sector 1 page 0), then `[sector][page][size][data]` chunks (sector 0 pages 0x92-0x99, sector 1 pages 1-24). An unregistered figure gets only write B at first; the game's later save sends A and B. The result decrypts (`AmiiboSerialization.decrypt_binary` returns `{:ok, _}`) and the registered figure scans cleanly in Kirby Air Riders. A removed tag is reported as status 0x07 with detail 0x41 (once, after a tag was reported); the console's remove-the-amiibo screens wait for it. Not verified: the exact meaning of the first slot chunk `(0, 4, 4)`, the poll status for a refused write (0x07 is a guess), and v2 figures (never written on the console).

## Host channel

The host protocol is the one in `firmware/picopad/src/host_protocol.c` (COBS packets, `[len16][cmd][payload][crc8]`). The dongle answers unknown-command (status 0x01, `HOST_STATUS_UNKNOWN_CMD`) to anything not in `src/host/host_commands.c`'s `COMMAND_TABLE`. Add each command as a handler in `src/host/handlers/` plus an entry in that table, with a test in `test/test_host_commands.c`. Payload formats below match the Pico firmware so the existing Elixir library works unchanged. Elixir side: `apps/picopad`.

Needed by `apps/picopad_proxy` (its Picopad page and connection status):

- [x] **Start advertising (0x02)** and **stop advertising (0x03)**. Done and verified on the dongle (2026-11-14): after a stop `get_status` reads disconnected and stays so (no re-advertise on disconnect); start gives advertising, pairing, ready as the console connects.
- [x] **Reconnect (0x40)**. Done and verified: ERROR with no stored pairing, OK after a stop with a stored pairing (advertising, then 0xE4, then pairing, ready), BUSY while connected. Not verified: BUSY while advertising only.
- [x] **Forget bonding (0x41)**. Done and verified: the link drops, 0xE6 is sent, the dongle advertises open, and the console on Change Grip/Order paired again by itself within 3 s.
- [x] **Events 0xE1, 0xE4, 0xE6.** Verified on hardware. 0xE1 (`<<0>>`) is sent each time the console starts a read; the console reads twice per scan on Enter Owner and Nickname, so expect two events per scan.
- [ ] **Reconnect failed (0xE5)** after the 30 s reconnect timeout is implemented but not verified on hardware (the console always reconnected at once).

Wanted, not needed by the proxy yet:

- [x] **Amiibo read (0x35) and read chunk (0x36).** Done and verified on the dongle: 0x35 replies `<<size::little-16, chunk_size>>` (AMIIBO_ERROR when nothing is loaded), 0x36 takes `<<chunk_index>>` and replies that slice (INVALID_PARAMS out of range). A dump read back after a console write passes `decrypt_binary`.
- [x] **Amiibo set readonly (0x38)**, payload `<<0 | 1>>`, reply OK. Done: the flag lives in `amiibo_store` and a read-only dump refuses write A and B (the console then sees status 0x07). Not tried on the console, and a load or clear resets the flag.

## Firmware and tooling

- [x] **Soft DFU.** Done and verified (2026-11-14): host reset with the bootloader target (0xF2, payload `<<1>>`, `Picopad.reset(pid, true)`) erases the last flash page of the app image and reboots; the factory Nordic bootloader sees an invalid app and stays in DFU (`nrfutil device list` shows "Open DFU Bootloader"), then `nrfutil device program --firmware <zip> --traits nordicDfu` flashes and the app boots. GPREGRET 0xB1 is ignored by this bootloader. Needs a working app to trigger: a dongle running a broken image still needs the RESET button. The first flash of this image needed one RESET press.
- [x] **Dongle build and flash script.** Done and run on hardware (2026-11-14): `sh scripts/build.sh` builds the dongle image and packages `build/dongle-app/dongle-nordicpad.zip` (application version is the Unix time, so every build is newer than the last; it refuses to build when the `CONN_INTERVAL_MIN` patch is missing from the NCS tree and prints the patch command). `sh scripts/flash.sh` reboots the running dongle into the bootloader over the host channel (soft DFU), flashes it by serial number and waits for it to return; it needs `NORDICPAD_DFU_SERIAL` if more than one bootloader device is attached. The Pico scripts are now `build_pico.sh` and `flash_pico.sh`.
